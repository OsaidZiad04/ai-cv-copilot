# Email My CV — isolated experiment report

Date: 2026-10-03. Branch: `feature/email-cv-delivery`. Base: stable `v1.0.1`, `b11b09bc1462f49e04e0fabf2abfea86febfdfb8`. No production merge or environment change.

## User flow

Create/edit CV → Email My CV → inspect profile email → optionally correct and save the profile email → review delivery-provider disclosure → Send My CV → sending/success/failure → continue preview, review, Print / Save PDF or clear session. The action is hidden when delivery is disabled. Focus enters the native dialog, Escape/cancel restores the trigger, status updates use a live region, and controls lock synchronously during sending.

## Architecture

CandidateProfile → existing browser `CvDocument` / print, or new server `CvPdfDocument` / in-memory PDF → fixed Brevo transactional message. A dedicated Node route validates `{profile}` and derives the only recipient from it. No Groq/provider changes, extra LLM calls, database, stored CV, public PDF URL, custom mail content, or experiment imports.

## PDF approach

`@react-pdf/renderer@4.9.0`, A4, dark text on white, one column, locally bundled static Noto Sans/Arabic fonts. Same production `hasText` and `visibleSections` helpers; conditional summary/education/projects/experience/skills/extras. Text and safe HTTP(S) link targets only. O01 contribution-only evidence survives with a generic Project label. Short extra sections stay together; long entries can continue onto page two. No logos, app controls, screenshots, rasterization or invented facts.

## Privacy impact

Explicit email consent shares email/PDF with Brevo and the destination mail service. The complete profile is temporarily processed by this app's server for rendering. The app intentionally stores/logs neither PDF nor profile server-side. Ending the browser session cannot delete provider/inbox copies or recall an already accepted message. Brief first-name greeting only; no CV body in HTML. TTL throttle hashes are pseudonymous operational state, not an email history database.

## Security review

Fixed endpoint/sender/subject/body; generated attachment only; strict top-level Zod request; bounded valid profile email; no recipient override, CC/BCC, arbitrary HTML or uploaded content. 256 KiB body, 60,000-character profile, 2 MB PDF limits. Same-origin browser protection where Origin is supplied; no external candidate URL fetches. Safe filename, HTTP(S) PDF links, generic errors, no-store responses and no sensitive logging.

Built browser assets were scanned internally for the configured Brevo key: no match. Four font files appear in the server route's build tracing. Secrets stay in ignored local configuration. No real recipient/key is included in committed QA artifacts.

Limits: this public self-reported profile does not prove mailbox ownership. Throttling is per warm instance, not durable/distributed, and a shared event source can hit its five-send limit. Provider quotas are mandatory operational protection. Review public exposure before activation.

`npm audit` found five advisories (one critical, three high, one moderate) in **unchanged baseline** Next.js/build/native dependencies. Baseline and branch package versions were compared; none of those packages changed and no new PDF package was named in the audit. No automatic dependency update was performed. Applicability/remediation belongs to a separate release review; this report does not claim a clean dependency audit.

## Real email test

One synthetic technical CV sent through the **local production build** using existing local Brevo configuration to the developer-supplied Gmail inbox, masked as `o***84@gmail.com`. Subject: `Your CV from AI CV Copilot`. Expected attachment: `Synthetic_CV_Student_CV.pdf`, one A4 page with the Research Paper Assistant evidence. The UI reached **CV sent**, demonstrating provider acceptance. A double-click while sending kept controls disabled; the client ref lock and provider-attempt tests cover single-attempt behavior. Test session was ended and refreshed back to landing afterward.

Inbox arrival, opening the received attachment and selection of its text await developer confirmation. Provider acceptance is not a delivery receipt. Local PDF samples open/render and extract correctly, but that does not independently prove the emailed attachment was opened in Gmail.

## Failure scenarios

Automated: missing key/sender, toggle off, invalid or overlong email, malformed profile/JSON, request over limit, arbitrary recipient/mail field, cross-origin browser request, provider 400/429/500, PDF failure/invalid bytes, render timeout, slow body input, send timeout, repeated recipient and source burst. Safe responses; no automatic retry or late-PDF send; no provider body/key leak.

Browser: 375px and 1440px dialog checks; valid/invalid correction; profile email changes visible in CV; server-disabled send yields friendly failure; cancel/Escape and restored focus; preview/review remain usable; corrected profile survives refresh; End & clear session plus refresh returns to landing; real send reached sending/success. Browser print capture remains unverified due to the tool limitation above. Existing 34 production regressions remain passing, including Guided/AI-compatible/O01/session/print assertions.

## Provider quota implications

Zero LLM calls added. One requested send is one Brevo attempt. No automatic retry. Actual account daily allowance must be verified in Brevo; the UI makes no invented quota claim. Warm-instance safeguards: recipient cooldown 60 seconds, source five sends/10 minutes, two active requests, maximum 1,000 expiring hashed keys. Network timeout may follow acceptance, so users are told to check the inbox before retrying.

## New dependencies

One direct application package: `@react-pdf/renderer@4.9.0` (59 installed transitive packages). Four open-source static font assets, license retained. Optional developer PDF QA uses existing Python/Poppler tooling; no paid package, API, storage or service introduced.

## New risks

Additional provider/recipient copies of a CV; quota/bounce/spam handling; per-instance abuse limits; renderer cold-start/CPU cost; duplicated presentation templates requiring parity regression; other scripts/emoji not comprehensively supported. Timers stop waiting but cannot force-cancel synchronous renderer CPU work. Acceptance can precede a lost response. No durable idempotency, mailbox verification or delivery-history UI is included.

Typical local warm synthetic PDF generation was approximately 8–170 ms depending on fixture (cold first case roughly 170–685 ms across test runs); these are local observations, not Vercel performance guarantees. Email network time is additional and bounded. PDF fixtures range roughly 12–26 KB. Preview runtime/cold-start validation is still required.

## Rollback / disable mechanism

Set `CV_EMAIL_SEND_ENABLED=false` and redeploy/restart only the intended environment. Missing flag defaults off. Print / Save PDF and the CV session remain available. No production variables were changed. See [`docs/EMAIL-CV-DELIVERY.md`](../../docs/EMAIL-CV-DELIVERY.md) for exact Preview-only setup and future approved production setup.
